## Overview

The API exposes endpoints to manage users, characters, guides and events, with JWT authentication and role-based access control (beginner, veteran and admin).

It is written in Go with Gin (HTTP), GORM (PostgreSQL) and Swaggo (Swagger documentation generated from handler comments). The code is organized **by feature**: each resource (user, character, guide, event) has its own folder with handler, service, DTOs and routes, and shared infrastructure lives in `internal/platform`.

## Tech Stack

- Go
- Gin
- GORM + PostgreSQL
- JWT (`golang-jwt/jwt`)
- bcrypt (`golang.org/x/crypto`)
- Rate limiting (`golang.org/x/time/rate`)
- Swaggo / Swag
- zap (structured logging)
- godotenv
- Air (hot reload during development)
- Docker / Docker Compose
- testify (tests)

## Environment Configuration

Copy `.env.example` to `.env` and adjust the values:

```env
APP_PORT=8080
APP_ENV=development

DB_HOST=localhost
DB_PORT=5432
DB_USER=postgres
DB_PASSWORD=postgres
DB_NAME=feel_the_night
DB_SSLMODE=disable

CORS_ORIGINS=http://localhost:3000,http://localhost:5173
JWT_SECRET=replace-with-a-random-secret-of-at-least-32-characters
```

| Variable | Required | Description |
|---|---|---|
| `JWT_SECRET` | yes | Secret used to sign tokens. Must be **at least 32 characters** long, otherwise the API refuses to start. To generate one: `openssl rand -base64 48`. |
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_SSLMODE` | yes | PostgreSQL connection. |
| `APP_PORT` | no | Local API port (default `8080`). In production, `PORT` takes precedence. |
| `APP_ENV` | no | `production` enables the trusted proxy configuration; any other value is treated as development. |
| `CORS_ORIGINS` | no | Comma-separated list of allowed CORS origins. Defaults to the usual local frontend ports. |
| `RENDER_EXTERNAL_HOSTNAME` | no | Set automatically by Render; adjusts the Swagger host and scheme (`https`) in production. |

`.env` is not committed. In production, variables come from the environment.

## Running with Docker

The project ships a `Dockerfile` (two-stage build: compiles with the Go image and copies only the binary into a minimal Alpine image that runs as a non-root user) and a `docker-compose.yml` that starts the API together with PostgreSQL.

Prerequisite: Docker with Compose (Docker Desktop on Windows).

### Full environment (API + database)

With `.env` in place (see [Environment Configuration](#environment-configuration)):

```bash
docker compose up --build
```

Compose starts Postgres, waits until it is ready (healthcheck) and then starts the API, which applies the migrations and becomes available at `http://localhost:8080` (Swagger at `/swagger/index.html`).

- The API reads your `.env` (`JWT_SECRET`, `CORS_ORIGINS`...), but the `DB_*` variables are set by Compose itself, pointing to the `db` service.
- `.env` is not baked into the image (it is in `.dockerignore`); secrets are only passed at runtime.
- The container runs the binary built at build time: after changing the code, run `docker compose up --build` again.

Useful commands:

| Command | What it does |
|---|---|
| `docker compose up --build` | Rebuilds the API and starts everything |
| `docker compose up -d` | Starts in the background |
| `docker compose logs -f api` | Follows the API logs |
| `docker compose down` | Stops the containers (keeps the database data) |
| `docker compose down -v` | Stops the containers and **deletes** the database |

To promote the first admin in the container database:

```bash
docker compose exec db psql -U postgres -d feel_the_night -c "UPDATE users SET role = 'admin' WHERE email = 'you@email.com';"
```

### Database only in Docker (recommended for development)

To keep `air`'s hot reload, run only Postgres in Docker and the API on your machine:

```bash
docker compose up -d db
air
```

The container database is exposed on port **5433** (to avoid clashing with a local Postgres), so in `.env` use:

```env
DB_HOST=localhost
DB_PORT=5433
```

Protected routes use the `BearerAuth` scheme. In the **Authorize** dialog, paste the `access_token` returned by login (with or without the `Bearer ` prefix).

## Authentication and Permissions

### Flow

1. Create an account with `POST /users`. Every new account starts as **beginner**.
2. Log in with `POST /auth/login` using email and password.
3. The response contains an `access_token` (valid for 15 minutes) and a `refresh_token` (valid for 7 days).
4. Send the access token on protected routes: `Authorization: Bearer <access_token>`.
5. When the access token expires (`401` with `"token expired"`), call `POST /auth/refresh` with the refresh token to get a new pair. The refresh token is rotated on every call, and the user's current role is reloaded from the database.

Login, refresh and sign-up are **rate limited per IP**: 5 attempts in a row, then 1 every 12 seconds. Beyond that, the API responds with `429` and a `Retry-After` header.

### Roles

| Action | Beginner | Veteran | Admin |
|---|---|---|---|
| Read any content | ✅ | ✅ | ✅ |
| Create guides | ❌ | ✅ | ✅ |
| Edit guides | ❌ | own guides only | any guide |
| Create/edit characters | ❌ | ✅ | ✅ |
| Create/edit events | ❌ | ✅ | ✅ |
| Edit own account | ✅ | ✅ | ✅ (any account) |
| Delete any content | ❌ | ❌ | ✅ |
| Look up users by email | ❌ | ❌ | ✅ |

### First admin

The role never comes from the request body. To create the first admin, sign up normally and promote the account directly in the database:

```sql
UPDATE users SET role = 'admin' WHERE email = 'you@email.com';
```

Then log in again (or use `/auth/refresh`): the role is stored inside the token, so the old access token keeps the previous role until it expires.

## Endpoints

| Method | Route | Access | Description |
|---|---|---|---|
| `GET` | `/health` | public | Health check |
| `POST` | `/auth/login` | public (rate limited) | Log in; returns access and refresh tokens |
| `POST` | `/auth/refresh` | public (rate limited) | Exchanges a refresh token for a new token pair |
| `POST` | `/users` | public (rate limited) | Sign up |
| `GET` | `/users?email=` | admin | Look up a user by email |
| `GET` | `/users/:id` | public | Public profile (without email) |
| `PATCH` | `/users/:id` | account owner or admin | Update the account |
| `DELETE` | `/users/:id` | admin | Delete a user |
| `GET` | `/characters?name=&type=` | public | List characters (optional filters) |
| `GET` | `/characters/:id` | public | Get a character |
| `POST` | `/characters` | veteran or admin | Create a character |
| `PATCH` | `/characters/:id` | veteran or admin | Update a character |
| `DELETE` | `/characters/:id` | admin | Delete a character (rejected with `409` if it has linked guides) |
| `GET` | `/guides?title=&page=&limit=` | public | List guides (paginated) |
| `GET` | `/guides/:id` | public | Get a guide |
| `POST` | `/guides` | veteran or admin | Create a guide (the author comes from the token) |
| `PATCH` | `/guides/:id` | author or admin | Update a guide |
| `DELETE` | `/guides/:id` | admin | Delete a guide |
| `GET` | `/events?title=&upcoming=&page=&limit=` | public | List events (paginated; `upcoming=true` shows only future events) |
| `GET` | `/events/:id` | public | Get an event |
| `POST` | `/events` | veteran or admin | Create an event (the author comes from the token) |
| `PATCH` | `/events/:id` | veteran or admin | Update an event |
| `DELETE` | `/events/:id` | admin | Delete an event |

Details for each route (body, responses and error codes) are in Swagger.

### Response formats

Errors always use the same format:

```json
{ "error": "message" }
```

Paginated lists (guides and events):

```json
{ "data": [], "page": 1, "limit": 20, "total": 0 }
```

Event dates use the `YYYY-MM-DD` format.

## Database

The connection is opened at startup using the `DB_*` variables. The schema is managed with **versioned migrations** using [Goose](https://github.com/pressly/goose): every database change is a numbered `.sql` file in `internal/platform/database/migrations/`.

On startup, the API automatically applies any migrations that have not run on that database yet. Goose records the applied versions in the `goose_db_version` table, so each migration runs exactly once.

Migrations are embedded in the binary (`//go:embed`), so deployments do not need to ship the folder.

### Creating a migration

Install the Goose CLI (once):

```bash
go install github.com/pressly/goose/v3/cmd/goose@latest
```

Generate the file from the project root (`-s` uses sequential numbering: `00003`, `00004`...):

```bash
goose -s -dir internal/platform/database/migrations create add_views_to_guides sql
```

Fill in both blocks of the generated file:

```sql
-- +goose Up
ALTER TABLE guides ADD COLUMN views BIGINT NOT NULL DEFAULT 0;

-- +goose Down
ALTER TABLE guides DROP COLUMN views;
```

- `Up` is the change; `Down` is how to undo it.
- The API applies the new migration on the next startup.
- If the change affects a model, also update the struct in `internal/models/models.go`.

Rules:

- **Never edit a migration that has already been applied.** It will not run again; to fix something, create a new migration.
- Migrations are the source of truth for the schema. GORM tags on the models do not create or alter tables.

### Checking the status

```bash
goose -dir internal/platform/database/migrations postgres "host=localhost user=postgres password=postgres dbname=feel_the_night sslmode=disable" status
```

### Soft delete

Deletes are **soft deletes**: the record gets a timestamp in `deleted_at` and stops showing up in queries, but stays in the table. That is why the unique indexes (user email, character name) only apply to non-deleted records.

## Tests

The project has two kinds of tests: **unit** tests, which run without a database or Docker, and **integration** tests, which exercise the whole API against a real PostgreSQL.

Unit tests live next to the code they test (`*_test.go` files). They currently cover:

- `internal/platform/jwt`: token generation and validation (including that a refresh token is not accepted as an access token, and vice versa);
- `internal/platform/middleware`: authentication and role checks;
- `internal/platform/database`: escaping text for `ILIKE` searches;
- `internal/event`: parsing dates in the `YYYY-MM-DD` format.

### Running

```bash
go test ./...              # all tests
go test ./... -v           # shows each test name and result
go test ./... -race        # detects unsynchronized concurrent access (e.g. rate limiter)
go test ./... -cover       # shows coverage per package
go test ./internal/platform/jwt/   # a single package
```

`-race` requires cgo: on Windows it needs a C compiler (gcc) installed; on Linux and macOS (and in CI) it works out of the box.

### Integration tests

They live in `tests/integration/` and test the whole API: they start a real PostgreSQL in a container (via [testcontainers-go](https://golang.testcontainers.org/)), apply the migrations, build the router with `app.NewRouter` and send HTTP requests with `httptest`. They cover the rules that only show up when the database and permissions work together:

- a veteran cannot edit another user's guide (403), but the author and admins can;
- a character with linked guides cannot be deleted (409);
- a guide with a nonexistent character is rejected (400);
- beginners cannot create content (403);
- the rate limit blocks the 6th consecutive login attempt from the same IP (429).

They require **Docker to be running**. Since they use the `integration` build tag, they are not part of the regular `go test ./...`; run them with:

```bash
go test -tags=integration ./tests/... -v
```

The first run downloads the Postgres image and takes longer; subsequent runs take a few seconds. The container is created and destroyed automatically on every run.

The helpers send each request from a different IP so the rate limiter does not interfere across tests. Each test uses its own emails, since they all share the same database.

**VS Code:** because of the build tag, the editor ignores these files by default. The project's `.vscode/settings.json` already enables the tag (`gopls.buildFlags` and `go.testTags`); if the editor still shows "No packages found", run `Go: Restart Language Server`.

### During development

Tests do **not** run in `air`, on purpose: air rebuilds on every save, and waiting for the tests would make reloads slow. To follow the tests while you code, run `gotestsum` in a separate terminal:

```bash
go install gotest.tools/gotestsum@latest
gotestsum --watch
```

It reruns the tests of the package you changed, without interfering with the API.

### Before pushing code

Run `go test ./...` before committing. To make sure you don't forget, you can add a git hook that runs the tests before every `git push` and aborts the push if any test fails. Create `.git/hooks/pre-push`:

```bash
#!/bin/sh
go test ./... || exit 1
```

On Linux/macOS, make it executable with `chmod +x .git/hooks/pre-push`. Hooks live only on your machine (they are not committed), so each team member needs to create their own.

### Sample data

To populate a local API with sample data:

```bash
pip install -r requirements.txt
python tests/seed_models.py
```

The script uses `BASE_URL` (default `http://localhost:8080`). Since the creation routes require veteran or admin, the account used by the seed must be promoted first.

## Notes

- The documentation in `docs/` is generated by `swag`. Do not edit those files by hand.
- Internal errors (database, timeout) are logged with zap and never exposed to the client, which only receives `"internal error"`.
- Every request has a 10-second timeout.
- In production (`APP_ENV=production`), the proxy IP ranges must be configured in `internal/app/routes.go` so the rate limiter can identify each client's real IP.
